A 3-billion-parameter OCR model.
Running in this tab.

franken_ocr hand-ports vision-language models into memory-safe Rust with model-specific CPU kernels — no PyTorch, no Python, no CUDA, no GPU, no FFI. The same code that ships as the focr CLI compiles to WebAssembly, so Baidu's Unlimited-OCR document model (int4, 2.8 GB) and the TrOMR sheet-music model (58 MB) run fully in your browser: your documents never leave this page — the CSP's connect-src 'self' makes that a browser-enforced promise, not a privacy-policy one.

Two models, both executed by hand-written Rust kernels compiled to wasm, entirely on your CPU, in this tab. TrOMR (58 MB) turns sheet-music scans into MusicXML and runs anywhere, phones included. Baidu Unlimited-OCR (2.8 GB int4, desktop browsers) parses document pages into Markdown — expect roughly 1–4 minutes per page depending on density and your core count; on cross-origin-isolated Chrome it decodes across 8 worker threads. Every download is SHA-256-verified against a pinned manifest and cached for next time.

    How it works
    
  
    
    
    
      
    A few models, every dimension fixed
    
      
    A general ML framework pays a generality tax on every op: dynamic dtype dispatch,
      arbitrary shapes, autograd bookkeeping. franken_ocr runs a small set of hand-ported
      models whose dimensions are known at compile time, so every kernel is written for
      its exact shapes. There is no generic runtime underneath.
    
    
    
    
    
      
    Correctness before speed, always
    
      
    Every model is certified against its Python reference through a parity ladder —
      preprocessing exact, per-op cosine ≈ 1.0, per-layer hidden states, logits, decoded
      tokens, end-to-end error rates. A faster kernel that drifts the output is reverted
      and recorded in a negative-evidence ledger. The browser build is the same code:
      the wasm MusicXML output on this page's smoke fixture is byte-identical to the
      native CLI's.
    
    
    
    
    
      
    Quantized, provably
    
      
    Checkpoints are transformed offline into .focrq artifacts: int8
      weights where measurement says it's safe, high precision where it isn't. Every
      accelerated int8 kernel ships with a bit-identical scalar oracle, and
      focr robot selftest re-proves the dispatched kernel on your
      CPU — including the browser's, where the wasm build reports its route the same way.

    The browser port, honestly
    
  
    
    The engine's inference core — model forwards, int8 kernels, preprocessing,
    tokenizers — is pure sync compute over byte buffers, so it compiles to
    wasm32-unknown-unknown with the async runtime, SQL run-store, and
    CLI feature-gated away. One code path serves native and wasm; parity is proven on
    the built artifact against the native CLI, not asserted from source.
  
    
  
    
    TrOMR (58 MB) is small enough to be interactive everywhere, phones
    included, on the serial simd128 build.
  
    
  
    
    Unlimited-OCR took five walls to get here. The CLI's int8 artifact
    is 4.16 GB — over wasm's 4 GiB ceiling — so the browser gets a wasm-only recipe:
    int4 (group-16/32) on the MoE expert bulk with importance-weighted clip search and
    activation-aware scale folding calibrated on real scanned pages, int8 on everything
    else resident, vision tower kept bf16. That's 2.8 GB. Then: runtime residency work
    (streamed per-block vision hydration, int8-resident embeddings — 5.7 → 3.6 GB peak);
    wasm32's 2 GiB single-allocation cap (the blob loads as segments cut at tensor
    boundaries); Chrome's refusal of multi-GB ArrayBuffers (weights stream from fetch
    into wasm memory, hashed incrementally, never materialized in JS); and a
    shared-memory threaded build (8 workers) beside a serial fallback for WebKit.
  
    
  
    
    Honest numbers, not marketing: on a 7-page corpus of repo fixtures
    and real 1870s–80s archive.org scans, the browser output is character-identical to
    the native CLI running the same artifact on 6 of 7 pages; the hardest dense
    newsprint page shows platform f32 drift (documented, with the same repetition-guard
    mitigation the CLI manual describes applied and labeled). Quantization fidelity vs
    the bf16 reference decode: exact-to-CER≤0.008 on clean pages, with a measured tail
    on degraded newsprint — the full receipts live in the repo's
    discrepancies ledger.
    A page takes 1–4 minutes in-tab. The CLI is faster and certified deeper; the tab
    needs zero installation and sends nothing anywhere.
  
    

    


    
  
    Install the CLI
    
  
    The full product — all five models, PDFs, batching, robot/agent mode — is a single
  static binary:
    
  
    curl -fsSL https://raw.githubusercontent.com/Dicklesworthstone/franken_ocr/main/install.sh | bash
focr pull tromr
focr ocr --model tromr.int8.focrq --task music score.png -o score.musicxml
    
  
    macOS (Apple Silicon + Intel), Linux (x86-64 + ARM64), Windows (x86-64 + ARM64).
  Runtime ISA dispatch picks NEON/SDOT/SMMLA or AVX2/AVX-VNNI/AVX-512-VNNI per host —
  one binary per architecture.
