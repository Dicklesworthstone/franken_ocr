Neural OCR engines in pure Rust.
Now running in this tab.

franken_ocr hand-ports vision-language models into memory-safe Rust with model-specific CPU kernels — no PyTorch, no Python, no CUDA, no GPU, no FFI. The same code that ships as the focr CLI compiles to WebAssembly, so the Polyphonic-TrOMR sheet-music model runs entirely in your browser: your image never leaves this page.

    How it works
    
  
    
    
    
      
    A few models, every dimension fixed
    
      
    A general ML framework pays a generality tax on every op: dynamic dtype dispatch,
      arbitrary shapes, autograd bookkeeping. franken_ocr runs a small set of hand-ported
      models whose dimensions are known at compile time, so every kernel is written for
      its exact shapes. There is no generic runtime underneath.
    
    
    
    
    
      
    Correctness before speed, always
    
      
    Every model is certified against its Python reference through a parity ladder —
      preprocessing exact, per-op cosine ≈ 1.0, per-layer hidden states, logits, decoded
      tokens, end-to-end error rates. A faster kernel that drifts the output is reverted
      and recorded in a negative-evidence ledger. The browser build is the same code:
      the wasm MusicXML output on this page's smoke fixture is byte-identical to the
      native CLI's.
    
    
    
    
    
      
    Quantized, provably
    
      
    Checkpoints are transformed offline into .focrq artifacts: int8
      weights where measurement says it's safe, high precision where it isn't. Every
      accelerated int8 kernel ships with a bit-identical scalar oracle, and
      focr robot selftest re-proves the dispatched kernel on your
      CPU — including the browser's, where the wasm build reports its route the same way.

    The browser port, honestly
    
  
    
    The engine's inference core — model forwards, int8 kernels, preprocessing,
    tokenizers — is pure sync compute over byte buffers, so it compiles to
    wasm32-unknown-unknown with the async runtime, SQL run-store, and
    CLI feature-gated away. One code path serves native and wasm; parity is proven on
    the built artifact against the native CLI, not asserted from source.
  
    
  
    
    What runs today: TrOMR (58 MB) — small enough to be interactive
    everywhere, phones included, on the serial simd128 build.
  
    
  
    
    What's in progress: the Baidu Unlimited-OCR lane. The shipped int8
    artifact is 4.16 GB — over wasm's 4 GiB memory ceiling before the first activation
    is allocated. Getting it into a tab requires a more aggressive, carefully-damage-
    controlled quantization: int4 (group-16) on the MoE expert bulk with
    error-compensated rounding and activation-aware scale folding, int8 everywhere else
    that stays resident. That lands at roughly 2.3 GB — a desktop-Chrome-class download
    in the same spirit as frankentts' 2 GB in-browser
    TTS. It ships when — and only when — the quantized artifact passes the same corpus
    error budgets the native release gates on. No preview toggles, no silently degraded
    output.
  
    

    


    
  
    Install the CLI
    
  
    The full product — all five models, PDFs, batching, robot/agent mode — is a single
  static binary:
    
  
    curl -fsSL https://raw.githubusercontent.com/Dicklesworthstone/franken_ocr/main/install.sh | bash
focr pull tromr
focr ocr --model tromr.int8.focrq --task music score.png -o score.musicxml
    
  
    macOS (Apple Silicon + Intel), Linux (x86-64 + ARM64), Windows (x86-64 + ARM64).
  Runtime ISA dispatch picks NEON/SDOT/SMMLA or AVX2/AVX-VNNI/AVX-512-VNNI per host —
  one binary per architecture.
